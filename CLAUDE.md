# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

The showcase site for theapps.app — a hub-and-spoke portfolio. This site is the hub: a homepage grid of app cards, each opening a case-study page. Each featured app (e.g. WhosIn) keeps its own product and domain elsewhere; this site only links out to it.

## Commands

```bash
npm install
npm run dev         # http://localhost:4321
npx astro dev stop  # stop the dev server
npm run build       # static output to dist/
npm run preview     # serve the built site
npm run check       # typecheck .astro files
```

No test suite. No lint script configured.

## Architecture

**Fully static.** `astro.config.mjs` has no adapter — `npm run build` emits plain HTML/CSS to `dist/`, no server runs in production. Don't add server-rendering, API routes, or anything that assumes a request-time backend without discussing it first; it breaks the deploy model.

**Apps are content, not code.** Each featured app is a Markdown file in `src/content/apps/`, validated against the Zod schema in `src/content.config.ts`. The filename becomes the route: `src/content/apps/foo.md` → `/apps/foo`, generated by `src/pages/apps/[...slug].astro` via `getStaticPaths()`. To add an app, copy `src/content/apps/_example.md` (its `_` prefix excludes it from the glob loader, so it never ships) — it documents every frontmatter field. Frontmatter typos fail the build with the offending file and field named, rather than rendering silently wrong.

- `status: live | building | planned` drives the badge shown on the card and case-study header (`src/components/StatusBadge.astro`).
- `stack` is an object keyed by section, not a flat list. The sections are defined once in `src/lib/stack.ts`; `src/content.config.ts` builds the Zod schema from that list, so adding a section there makes it valid frontmatter everywhere at once. The schema is `.strict()` — a key an app file invents (`qa:` instead of `testing:`) fails the build naming the file and the key, rather than rendering as a section nobody sees. Value conventions (version inline, ` — ` for the role qualifier, `~` prefix for not-yet-wired-up) are documented in that file and in `_example.md`. One trap the schema can't catch: a YAML flow sequence splits on commas, so `[GitHub Actions — lint, test]` is two entries rather than one, and it renders as two plausible rows instead of failing. Quote any value containing a comma.

`/stack` (`src/pages/stack.astro`) renders the matrix — sections down, apps across, every section shown including the empty ones, since a blank cell next to a filled one is the signal. It's in the nav (Apps · Stack · About). Its intro frames it as what the apps are built on, not a list of skills, and says openly that they're built with AI assistance — keep that framing if the copy changes.
- `order` controls homepage sort (lower first).
- `draft: true` keeps a file in the repo but off the site entirely — no card, no case study, not on `/stack`.
- `unlisted: true` is the weaker version: no homepage card, but the case study and the `/stack` column both stay. `theapps.md` — this site's own entry — is the case, so the stack page has a column for the site you're reading without the hub advertising itself alongside the apps it points at.
- `url` is optional — omit it if the app has nothing public to link to yet.
- `repo` is optional and renders a GitHub mark (`src/components/RepoLink.astro`) on the card and case study. Omit it for anything whose source is private; a link to a 404 is worse than no link.
- `logoDark` is optional and replaces `logo` in dark mode (`src/components/AppLogo.astro` renders both; CSS picks one). Only add it if the plain logo doesn't read on a dark background, and use the app's own dark asset rather than recolouring one here — `fphelp_logo_dark.png` is a copy of fphelp's `public/logo-dark.png`. Both logos are copies, so they go stale if the sibling repo redraws its logo.

**Styling is hand-rolled Tailwind v4**, not a component library. Theme tokens (colors, font) live in the `@theme` block in `src/styles/global.css`; case-study prose is styled there too under `.prose` rather than via `@tailwindcss/typography`. Shared visual language lives in that one file — check it before hardcoding a color or spacing value in a component.

**Dark mode** follows the OS (`prefers-color-scheme`) until the nav toggle (`src/components/ThemeToggle.astro`) pins a choice in `localStorage`. The dark palette in `global.css` is written twice, once inside the media query and once under `:root[data-theme='dark']`, so a new color token needs a dark value in **both** blocks. Missing one gives a theme that's right for OS-dark users and wrong for toggle users, or the other way round. In components, plain `dark:` classes work: the variant is redefined at the top of that file to cover both cases, not just the OS setting. The inline script in `Base.astro`'s `<head>` applies the saved choice before first paint. Keep it inline and ahead of the stylesheet, or the page flashes the wrong theme on load. The `theme-color` tags above it hardcode `--color-paper` for each theme as hex, so change them when the paper colour changes. `.prose pre` swaps colours along with the page, so a code block would render as a light box in dark mode. It needs its own dark colours before a case study uses one.

**Two source-of-truth pairs that must stay in sync:**
- `site` in `astro.config.mjs` and `SITE_URL` in `src/consts.ts` (sitemap/canonical URLs are generated from these).
- Any app's `status`/`url` here vs. that app's actual deploy state — this repo doesn't know when a sibling project ships, so it has to be updated by hand.

**MDX is available but unused** — `whosin.md` is plain Markdown. Reach for `.mdx` only if a case study needs an embedded component.

## Deploy

Cloudflare (Workers → Import a repository, or Pages if that tab still exists). Build command `npm run build`, output directory `dist`. Push to `main` deploys; every push to any other branch builds a preview, PR or not — `https://<branch>.theapps-7nt.pages.dev`, and the "Cloudflare Pages" check on the commit links it. See README.md for the full walkthrough, including custom-domain and email-routing setup.

**The site is live and indexable** as of 2026-09-21. It spent its first weeks online under a `noindex, nofollow` meta so the first impression would be deliberate; that tag is gone and `public/robots.txt` advertises the sitemap again. If it ever needs to go back to being unlisted, use the meta tag rather than `Disallow: /` in robots.txt — a blocked crawler never fetches the page, so it never reads the noindex, and bare URLs can still be indexed from links elsewhere.

**Link previews** come from `public/og.png`, referenced as an absolute URL in `src/layouts/Base.astro`. It's one static card for the whole site; `og:title` and `og:description` stay per-page. See README.md.

**Internal links end in a slash** (`/about/`, `/apps/whosin/`). Astro builds `about/index.html`, and Cloudflare 308-redirects `/about` to `/about/` — an extra round-trip on every click, and it appeared to skip the page crossfade. `npm run dev` serves both forms, so the difference only shows on a preview. Canonicals and the sitemap already use the slash form.

**Redirects** live in `public/_redirects`, which Cloudflare serves as-is. Case studies were at `/work/<app>` until 2026-09-24, after the site was already indexed; the `/work/…` rules keep those old URLs and search results working, and point straight at the trailing-slash form so there's one hop, not two. Leave them in place. The file only runs on Cloudflare, so test it on a preview URL, not `npm run dev`. The `www` → apex redirect is a Cloudflare Redirect Rule, not a line in this file, since `_redirects` only matches paths; README.md has its settings.

**`src/pages/404.astro` must exist.** Cloudflare only returns a real 404 when `dist/404.html` is present. Without it, the site is treated as a single-page app, and every unknown URL gets the homepage with a 200: soft 404s that Search Console flags, and mistyped links that look like they worked.
